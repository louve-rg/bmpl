# M6.2 — Marketplace Variant Availability, "All" Filtering & Brand Image

Client-feedback adjustments to the customer marketplace, product detail, vendor
editor, storefront preview, and creation flow. Implemented through shared data +
rendering logic so the live marketplace and the vendor Storefront Preview behave
identically.

## Root causes → fixes
1. **Variants hidden until a selection was made / dropdowns showed every configured
   value.** The detail page derived option pickers from the raw option-value
   definitions, not from purchasable variants. → A shared `variant-availability`
   util derives customer-selectable values from the **valid variant set** only,
   combination-aware, and the page shows the full **variant lineup on open** (no
   selection required).
2. **Brand vs gallery vs variant image was inferred from one `isPrimary` flag.** →
   Added an explicit `ProductImage.isBrandImage` role (at most one per product), a
   derived `role` (`BRAND`/`GENERAL`/`VARIANT`), and dedicated set/clear endpoints.
3. **Card image had no brand precedence; the detail gallery could include the brand
   image.** → `primaryUrls` (cards/search/category/storefront) now uses brand-first
   precedence; the detail gallery (`listGallery`) excludes the brand image.

## Availability logic (source of truth = valid variants)
The marketplace exposes only values backed by a variant that is published + active +
approved + in-stock (or unlimited/backorderable). `availableValuesForOption` is
**combination-aware** — each option dropdown lists only values that still resolve to
an available variant given the other current selections, so impossible combinations
can't be chosen. Zero-stock-only values are hidden. The purchase button reflects the
true state: **Unavailable** / **Select options** / **Add to cart** / **Out of stock**
(never "Select options" as a fallback after an invalid pick). The same
`apps/web/lib/variant-availability.ts` powers the live page and the vendor Storefront
Preview.

## "All {Option}" browsing state
Customer dropdowns default to `All {pluralized option name}` (e.g. "All Fragrances",
"All Colors", "All Sizes") — a display-only filter, never a stored variant value and
never entering the cart. A specific variant must still be selected before add-to-cart
for products with required variants. Labels are generated from the vendor's option
name with sensible English pluralization (fallback `All {name}`).

## Brand Image
`isBrandImage` (schema, additive) is the marketplace listing image role — used for
cards / search / category / storefront grid via the precedence **Brand Image →
product primary → variant primary → fallback**. It is **never** shown in the product
detail gallery or a variant thumbnail row and is **never** variant-scoped (set-brand
detaches it from any variant and clears its gallery-primary flag). Exactly one active
per product; setting another replaces the designation without deleting files;
clearing returns it to the general gallery. Vendor editor: a dedicated Brand Image
slot + "Set as Brand Image" on other images + role chips. Endpoints:
`POST /vendor/products/:id/images/:imageId/brand`, `DELETE …/brand`. Marketplace API:
detail returns `brandImageUrl` + a gallery that excludes the brand image; each image
carries `isBrandImage` + `role`.

## Product detail variant lineup
Beneath the main image, one thumbnail/card per **available** variant (hidden if
unpublished/inactive/zero-stock), using the variant's own primary image + display
name; selecting one switches the gallery/title/price/SKU/inventory. In the "All"
state the lineup shows every available variant.

## Creation flow
The initial product-creation button is **"Next"** (not "Create Product") — the create
step navigates to the editor where options/variants/images/inventory are completed;
existing save/draft/navigation logic is unchanged (progress preserved by the
create→edit redirect). Final actions (Save Draft / Submit / Publish / Update) remain
at their steps. *(Publish-on-create policy is unchanged — flipping it to draft-first
would be a separate approved workflow change.)*

## Data model / API
`ProductImage.isBrandImage` (migration `20260806120000_brand_image_role`, additive
boolean + index; existing images default false → no behavior change for existing
products). Serialized image role is explicit (`isBrandImage` + `role`); variants
carry `title`/`displayName`/`optionLabel` + `availability`; detail exposes
`brandImageUrl`; cards use brand-first `primaryUrls`.
