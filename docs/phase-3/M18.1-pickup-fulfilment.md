# Phase 3 · M18.1 — Pickup Fulfilment

Gives PICKUP vendor-orders a real **completion signal** — the analogue of a delivery
reaching `DELIVERED` — so downstream features (M19 review eligibility) have an
authoritative "collected" event. A pickup order is **not** complete merely because it
was placed.

## Workflow
1. **Vendor marks ready:** `POST /vendor/orders/:vendorOrderId/ready-for-pickup` →
   `VendorOrderStatus` `PENDING → READY_FOR_PICKUP`, stamps `readyForPickupAt`, issues
   a 4-digit **pickup PIN** (held by the customer), and notifies the customer.
2. **Customer reveals the PIN:** `GET /orders/vendor-orders/:vendorOrderId/pickup-pin`
   (own order only) — shown at collection. The PIN is **never** exposed on the vendor's
   order view.
3. **Vendor confirms collection:** `POST /vendor/orders/:vendorOrderId/confirm-pickup`
   `{ pin }` → verifies the PIN (constant-time; attempt-capped at 5 → locked, audited
   `VENDOR_ORDER_PICKUP_PIN_FAILED`), transitions `READY_FOR_PICKUP → PICKED_UP`, stamps
   `pickedUpAt`, and **finalizes inventory exactly once** (guarded by
   `VendorOrder.inventoryFinalizedAt`, via `InventoryService.finalizeReservation`).
4. **Admin override:** `POST /admin/orders/vendor-orders/:vendorOrderId/confirm-pickup`
   `{ reason }` — requires `orders.manage` + a reason; confirms without the PIN.

Idempotent (a repeated confirm returns `PICKED_UP` without re-finalizing inventory).
Ownership-scoped (only the vendor who owns the vendor-order and the customer who owns
the order participate; others get `404`). Timeline/events are recorded via the audit
log (`VENDOR_ORDER_READY_FOR_PICKUP`, `VENDOR_ORDER_PICKED_UP`, `INVENTORY_FULFILLED`)
+ in-app notifications.

## Boundaries preserved
Payment and **settlement** boundaries are unchanged: M18.1 does **not** trigger
settlement for pickup orders (that remains a separate, future money-flow decision — no
new escrow release here). Only inventory finalization occurs on collection.

## Data model
`VendorOrderStatus` += `READY_FOR_PICKUP`, `PICKED_UP`. `VendorOrder` +=
`readyForPickupAt`, `pickedUpAt`, `pickupPin`, `pickupPinAttempts`,
`inventoryFinalizedAt` (migrations `20260807120000_pickup_fulfilment_enums` +
`20260807121000_pickup_fulfilment`; additive). Delivery orders are unaffected (they
complete via `OrderDelivery.status = DELIVERED`).

## Review eligibility (feeds M19)
- Delivery vendor-orders: review-eligible after `OrderDelivery.status = DELIVERED`.
- Pickup vendor-orders: review-eligible **only** after `VendorOrder.status = PICKED_UP`.
- Cancelled / rejected / pending / uncollected orders: not eligible.

## Tests
`pickup-fulfilment.integration.spec.ts` (+4): ready → PIN reveal → confirm →
`PICKED_UP` + inventory finalized once (quantity + reserved decremented, one FULFILLED
change); idempotent second confirm (no double-finalize); ownership isolation + pickup-
only guard + attempt-cap lock + admin override (reason required, `orders.manage`-gated);
delivery-order rejected for pickup. No settlement/payment mutation. Suite: 302
integration, 30 unit, 17 shared.
